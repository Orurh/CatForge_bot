# Проверки и обновления CatForge

Обновлено 11.09.2026. Схема для одной Linux amd64 машины: GitHub Actions
проверяет код, Git-тег выпускает пару образов, оператор запускает одну команду
на сервере. Перенос данных и настройка самого компьютера — отдельный первый шаг.
Автоматического обновления на каждый push нет.

## Что выполняет GitHub Actions

Workflow [ci.yml](../.github/workflows/ci.yml) работает на push веток и тегов,
pull request и ручной запуск проверки. Он:

1. Собирает оба Docker-образа; сборка C++ выполняет CTest.
2. Поднимает отдельные PostgreSQL 16 и движок со случайными локальными портами.
3. Запускает `go test -race -count=1 ./...`, `go vet ./...`, Python-тесты,
   проверку Compose и Prometheus config/rules. Интеграционные переменные
   установлены: тесты миграций, платежей и игрового состояния не пропускаются.
4. Удаляет только временные контейнеры и данные CI. Игровой бот не запускается;
   реальные Telegram/AI-ключи не нужны.
5. Только при push тега `v[0-9]*`, после всех проверок передаёт **те же собранные
   образы** в отдельную задачу публикации. Повторной сборки при публикации нет.

Образы: `ghcr.io/owner/repository/bot:sha-<полный SHA>` и
`ghcr.io/owner/repository/engine:sha-<полный SHA>`. SHA сохраняется также в OCI label.
Публикация использует штатный `GITHUB_TOKEN` с `packages: write` только в этой
задаче. Секретов сервера, Telegram и AI в Actions нет.

После первого push убедиться, что Actions разрешены в репозитории. При наличии
ruleset/branch protection сделать `verify` обязательной проверкой. Это настройка
GitHub, локальный workflow не включает её сам. Если пакет с таким именем уже
существует, выдать репозиторию доступ к нему в настройках Packages.

Публичные образы можно скачивать без входа. Для закрытых пакетов на сервере
нужен вход `docker login ghcr.io` с доступом `read:packages`; доступ Git к
закрытому репозиторию настраивается отдельно. Не хранить пароли в Git или
аргументах shell-команд. Выпуск не меняет видимость репозитория/пакетов.

Локально те же проверки запускает `bash scripts/ci.sh`. Нужны Docker Compose,
Go из `go.mod`, Python 3 и доступ к Docker. Тестовая БД использует tmpfs.
Образы CI остаются в локальном Docker; они не заменяют работающие контейнеры.

## Первый запуск на другом компьютере

Требуются Linux amd64, Git, Python 3 и Docker Compose с поддержкой `!override`
(2.24.4+; локальная проверка выполнена на 2.31). Для круглосуточной машины
предпочтителен Docker Engine с автозапуском системного сервиса. После установки
проверить перезагрузкой, что стек поднялся. Для Docker Desktop отдельно проверить
запуск без ручного входа пользователя; `restart: unless-stopped` сам этого не делает.

Для машины за домашним роутером можно оставить polling и
`docker-compose.dev.yml`: ему не нужны публичный домен и входящий HTTPS.
Имя файла не обязывает переходить на webhook при переезде. `APP_ENV` и настройки
AI задаются отдельно в `.env`. Webhook-конфигурация остаётся доступна.

1. Клонировать репозиторий в постоянный каталог `catforge-bot` и выбрать
   проверенный тег. На сервере не редактировать tracked-файлы.
2. Перенести `.env` отдельно от Git, настроить локальные секреты мониторинга,
   права каталога backups и AI-провайдер. Bridge — отдельный локальный сервис;
   образы бота его не устанавливают. См. [runbook](BETA_RUNBOOK.md) и
   [мониторинг](MONITORING.md).
3. Остановить старый бот, сделать окончательный бэкап, восстановить его в БД
   нового хоста. Запускать новый бот только после восстановления; два процесса
   с одним Telegram token одновременно не запускать.
4. Первый стек можно собрать из выбранного тега по runbook. Настроить и проверить
   backup timer, внешнюю копию, readiness и уведомления. Все команды Compose
   должны использовать один project name, например `-p catforge-bot`.
5. Подготовить локальную конфигурацию обновления:

   ```bash
   mkdir -p .deploy
   cp deploy/host.example.json .deploy/host.json
   chmod 700 .deploy
   chmod 600 .deploy/host.json .env
   ```

   В `image_prefix` вписать реальный `ghcr.io/owner/repository` **в нижнем регистре**.
   В `project` указать имя **уже работающего** Compose-проекта. `compose_files`
   должен точно соответствовать запуску: базовый файл, monitoring и, если
   подключён, `docker-compose.alerts.yml`. Локальный `docker-compose.override.yml`
   автоматически не подхватывается. Пример host.json рассчитан на polling + monitoring.

`.deploy/`, `.env`, бэкапы и секреты исключены из Git; `.deploy/` также исключён
из Docker context и текстового экспорта кода. Использовать одну серверную копию
репозитория: блокировка обновления действует внутри её `.deploy/`.

## Обычный выпуск

На рабочем компьютере сохранить нужные изменения в коммит и отправить ветку.
После успешного CI создать новый тег на выбранном коммите и отправить его:

```bash
git tag v0.1.0-beta.1
git push origin v0.1.0-beta.1
```

Имя приведено как пример; каждый следующий выпуск получает новый тег.
Не переставлять выпущенные теги на другой коммит. Дождаться успешных **verify
и publish** в Actions тега: зелёная проверка ветки ещё не означает публикацию образов.

На сервере из корня checkout:

```bash
bash scripts/update.sh v0.1.0-beta.1
```

Скрипт сам получает указанный тег из `origin`, скачивает обе версии, проверяет
SHA label и фиксирует образы по registry digest. Затем переключает чистый
checkout точно на этот коммит. Отдельный `git pull` не нужен; после обновления
нормален detached HEAD. Публикация нового тега сама сервер не обновляет.

Перед остановкой бот должен быть healthy. При изменении инфраструктуры
(PostgreSQL, volumes, networks, мониторинг или адрес БД) скрипт откажет до простоя:
такие изменения сначала отдельно проверяются и устанавливаются на хосте.
Обычное обновление затрагивает только bot и game-engine; секреты остаются локальными.

Последовательность: скачать оба образа → проверить конфигурацию → остановить
bot → `pg_dump -Fc` и `pg_restore --list` → установить game-engine → запустить
bot с миграциями → дождаться healthy и выполнить `/app/bot healthcheck`.
Проверка архива подтверждает его формат; регулярное пробное восстановление
в отдельную БД по-прежнему обязательно.

Состоявшийся выпуск записывается в `.deploy/last-success.json`, текущие digest —
в `.deploy/current.json`, история и предыдущие image IDs — в `.deploy/history/`.
Архив `backups/pre-update-*.dump` имеет права 600 и не перезаписывается. Предыдущим
образам добавляются локальные rollback-теги. Скрипт не удаляет историю и бэкапы:
контролировать диск и сохранять нужные копии вне хоста.

Для дальнейших ручных операций с контейнерами **добавлять текущий overlay**:

```bash
docker compose -p catforge-bot -f docker-compose.dev.yml \
  -f docker-compose.monitoring.yml -f .deploy/current.json ps
```

Если включён alerts overlay, также добавить его перед `.deploy/current.json`.
`up --build` после перехода на образы не нужен. `/readyz` проверяет HTTP-процесс,
БД и совместимость RPC движка; доступность Telegram/AI и живую команду проверить
отдельно после выкладки.

## Если обновление не удалось

- Ошибка Git, скачивания или несовпадение версий: работающий бот не остановлен.
- Ошибка подготовки/бэкапа до активации: checkout возвращается на прежнюю версию,
  уже существующий контейнер бота запускается и проверяется. Неуспешное
  восстановление запуска сохраняет `.deploy/pending.json` для разбора.
- Ошибка после начала активации: бот останавливается, сохраняются новый checkout,
  `.deploy/pending.json`, candidate/previous image IDs и предмиграционный бэкап.
  Новый вызов update блокируется. Старый бинарник автоматически не запускается:
  новая схема уже могла примениться.
- После отключения питания или принудительного завершения процесса также
  сначала разобрать `pending.json` и фактическое состояние контейнеров.

Для диагностики использовать выбранные Compose-файлы и `images.json` из каталога
`history`, указанного в pending, затем `ps` и `logs --tail=100 bot game-engine`.
Не публиковать логи с персональными данными и секретами.

Если достаточно исправить зависимость, можно повторно запустить **ту же новую
пару образов** с этим `images.json` и проверить readiness. После успешного
восстановления скопировать этот файл в `.deploy/current.json`, сохранить pending
в историю с результатом и убрать блокирующий `.deploy/pending.json`.

Возврат старого кода допустим только после проверки совместимости миграций.
При несовместимой схеме восстановить предмиграционный архив в **новую БД**,
переключить `DATABASE_URL`, вернуть `previous_revision` и использовать
`previous-images.json` как последний Compose overlay. Данные, принятые после
архива, могут потребовать отдельного переноса/сверки; для Stars сверить ledger
и историю Telegram. Не применять `goose down` или восстановление поверх живой БД
автоматически. После проверки закрепить выбранные образы в current.json и
архивировать pending. Не удалять рабочий PostgreSQL volume.

## Что настраивается позже

На новой машине — автозапуск Docker, внешний бэкап и его восстановление,
получатель тревог, внешний uptime/dead-man monitor. После нескольких успешных
ручных выпусков этот же сценарий можно запускать таймером для одобренных релизов.
Таймер автоматической установки сейчас не добавлен.

Официальные справочники: [публикация Docker-образов через Actions](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images),
[Compose up и ожидание health](https://docs.docker.com/reference/cli/docker/compose/up/).
