# Проверки и автоматический деплой CatForge

Схема: push/merge в `main` → GitHub Actions → тесты и сборка → публикация
проверенных образов в GHCR → сервер проверяет результат каждые пять минут.
Другие ветки и pull request проходят CI, но не публикуются и не деплоятся.
Ручной workflow_dispatch выполняет только проверки. Теги больше не запускают выпуск.

## GitHub Actions

Workflow [ci.yml](../.github/workflows/ci.yml) собирает Go-бота и C++-движок,
выполняет CTest, Go race tests/vet, интеграционные проверки с отдельной PostgreSQL,
Python-тесты, проверку Compose и конфигурации мониторинга. Реальный бот в CI не запускается.
После успешного verify задача publish загружает **те же образы**, без повторной сборки:

- `ghcr.io/orurh/catforge_bot/bot:sha-<полный SHA>`
- `ghcr.io/orurh/catforge_bot/engine:sha-<полный SHA>`

Права packages:write есть только у задачи publish. На сервере образы фиксируются
по digest; OCI label обязан совпадать с коммитом. Требуется Linux amd64.

Для main рекомендуется branch protection с обязательной проверкой verify:
feature-ветка → pull request → успешный CI → merge. Прямой push в main также
запустит выпуск. Настройка workflow сама по себе не запрещает прямые push.

## Подготовка сервера

Требуются Docker Compose 2.24.4+, Python 3, Git, systemd и доступ к GitHub/GHCR.
Код находится в чистом checkout. `.env`, `.monitoring-secrets/`, `.deploy/` и
дампы остаются на сервере и не входят в Git. Сохранить существующее имя Compose
проекта: его смена может подключить другой volume PostgreSQL.

Создать `.deploy/host.json` по [примеру](../deploy/host.example.json).
Указать фактический `project` и полный список `compose_files`.
Локальные overlay (например, прокси) хранить в `.deploy/` и явно добавить в этот
список. Остальные Compose-файлы должны быть tracked. Не оставлять локальные
изменения или untracked файлы в серверном checkout вне игнорируемых каталогов.

Публичные GHCR-пакеты доступны без входа; первоначально опубликованные пакеты
могут быть закрытыми. Для закрытых образов выполнить на сервере `docker login
 ghcr.io` под пользователем службы с read:packages. GitHub API для публичного
репозитория работает без токена; при необходимости `GH_TOKEN` хранится в
`~/.config/catforge-deploy.env` с правами 600. Токен должен иметь только чтение
Actions/репозитория; токены Telegram и AI для деплоя не нужны.

Проверить вручную из checkout:

```bash
python3 scripts/auto_update.py
```

Скрипт проверяет точный текущий SHA main и успешный push-run `ci.yml` для него.
Если main продвинулся, CI не завершился или упал — работающая версия остаётся.
Успешный SHA повторно не устанавливается. Незавершённый деплой блокирует следующий.

Для пользователя с доступом к Docker установить пользовательский таймер:

```bash
python3 scripts/setup_auto_update.py
systemctl --user status catforge-deploy.timer
journalctl --user -u catforge-deploy.service -n 50
```

Если у пользователя нет доступа к Docker, администратор может установить
системную службу с `User=<пользователь>` и `SupplementaryGroups=docker`;
в этом случае применять `sudo systemctl` без `--user`. Не устанавливать оба таймера.
Служба должна запускать `scripts/auto_update.py` из постоянного checkout,
иметь `UMask=0077`, `TimeoutStartSec=45min` и таймер `OnUnitInactiveSec=5min`.
GitHub не подключается к серверу: входящие порты или self-hosted runner не нужны.

На новой машине отдельно восстановить данные, настроить ежедневный backup,
мониторинг и секреты. Старый и новый бот не должны работать с одним Telegram token.

## Ручное обновление и диагностика

Основной путь — `auto_update.py`, проверяющий успешный CI. Для диагностики
оператор может вызвать `bash scripts/update.sh --main-sha <полный SHA>`: эта
команда проверяет принадлежность текущему main и образы, но сама не запрашивает CI.
Старый интерфейс `update.sh v...` оставлен для уже опубликованных выпусков.

Перед остановкой бот должен быть healthy. При изменении инфраструктуры
(PostgreSQL, volumes, networks, мониторинг или адрес БД) скрипт откажет до простоя:
такие изменения сначала отдельно проверяются и устанавливаются на хосте.
Обычное обновление затрагивает только bot и game-engine; секреты остаются локальными.

Последовательность: скачать оба образа → проверить конфигурацию → остановить
bot → `pg_dump -Fc` и `pg_restore --list` → установить game-engine → запустить
bot с миграциями → дождаться healthy и выполнить `/app/bot healthcheck`.
Проверка архива подтверждает его формат; регулярное пробное восстановление
в отдельную БД по-прежнему обязательно.

Состоявшийся выпуск записывается в `.deploy/last-success.json`, текущие digest —
в `.deploy/current.json`, история и предыдущие image IDs — в `.deploy/history/`.
Архив `backups/pre-update-*.dump` имеет права 600 и не перезаписывается. Предыдущим
образам добавляются локальные rollback-теги. Скрипт не удаляет историю и бэкапы:
контролировать диск и сохранять нужные копии вне хоста.

Для дальнейших ручных операций с контейнерами **добавлять текущий overlay**:

```bash
docker compose -p catforge-bot -f docker-compose.dev.yml \
  -f docker-compose.monitoring.yml -f .deploy/current.json ps
```

Если включён alerts overlay, также добавить его перед `.deploy/current.json`.
`up --build` после перехода на образы не нужен. `/readyz` проверяет HTTP-процесс,
БД и совместимость RPC движка; доступность Telegram/AI и живую команду проверить
отдельно после выкладки.

## Если обновление не удалось

- Ошибка Git, скачивания или несовпадение версий: работающий бот не остановлен.
- Ошибка подготовки/бэкапа до активации: checkout возвращается на прежнюю версию,
  уже существующий контейнер бота запускается и проверяется. Неуспешное
  восстановление запуска сохраняет `.deploy/pending.json` для разбора.
- Ошибка после начала активации: бот останавливается, сохраняются новый checkout,
  `.deploy/pending.json`, candidate/previous image IDs и предмиграционный бэкап.
  Новый вызов update блокируется. Старый бинарник автоматически не запускается:
  новая схема уже могла примениться.
- После отключения питания или принудительного завершения процесса также
  сначала разобрать `pending.json` и фактическое состояние контейнеров.

Для диагностики использовать выбранные Compose-файлы и `images.json` из каталога
`history`, указанного в pending, затем `ps` и `logs --tail=100 bot game-engine`.
Не публиковать логи с персональными данными и секретами.

Если достаточно исправить зависимость, можно повторно запустить **ту же новую
пару образов** с этим `images.json` и проверить readiness. После успешного
восстановления скопировать этот файл в `.deploy/current.json`, сохранить pending
в историю с результатом и убрать блокирующий `.deploy/pending.json`.

Возврат старого кода допустим только после проверки совместимости миграций.
При несовместимой схеме восстановить предмиграционный архив в **новую БД**,
переключить `DATABASE_URL`, вернуть `previous_revision` и использовать
`previous-images.json` как последний Compose overlay. Данные, принятые после
архива, могут потребовать отдельного переноса/сверки; для Stars сверить ledger
и историю Telegram. Не применять `goose down` или восстановление поверх живой БД
автоматически. После проверки закрепить выбранные образы в current.json и
архивировать pending. Не удалять рабочий PostgreSQL volume.

## Остановка автоматического деплоя

```bash
systemctl --user disable --now catforge-deploy.timer
```

Для системной службы: `sudo systemctl disable --now catforge-deploy.timer`.
Остановка таймера не прерывает уже начавшееся обновление. Не прерывать службу
во время миграций; состояние неудачного обновления описано выше.
